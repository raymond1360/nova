# Claude Code 提示词：Nova v0.1.0 UI/UX 设计阶段

你现在是 Nova v0.1.0 的产品设计负责人兼首席 UI/UX 设计师。项目目录是 `D:\nova`。

## 一、本轮任务性质

本轮只完成 Nova v0.1.0 的界面与用户体验设计，不进入正式业务功能开发，不改动现有核心业务代码，不安装新依赖，不提交、不推送、不发布。

你的工作不是简单“美化现有页面”，而是基于仓库中的真实产品文档、现有代码、当前界面和技术约束，为 Nova v0.1.0 建立一套可直接指导后续开发的完整 UI/UX 设计方案。

设计完成后先等待用户确认。未获得用户明确确认，不得开始实现正式界面。

- Codex：承担独立代码审核、质量检查和复审工作。

## 四、产品定位

Nova 是面向 Windows 10/11 的独立桌面客户端，是普通人与 Codex、Claude Code 之间的“开发协调与验收层”。它不是 IDE，不是代码编辑器，不是终端外壳，也不是面向程序员的复杂 Agent 控制台。

目标用户是：

- 0 技术基础；
- 0 代码经验；
- 不理解 Git、CLI、diff、SHA、退出码、依赖、构建等术语；
- 只希望用日常语言说明“我想做什么”，然后知道目前做到哪一步、有没有问题、下一步该做什么。

核心价值：用户用自然语言提出需求，Claude Code 完成开发，Codex 独立审核，Claude Code 根据审核结果修改，Codex 二次复审，最后由用户确认效果。

核心体验原则：

> 换 AI，不换项目，不重新解释。记忆属于项目，不属于某一个 AI。

## 五、v0.1.0 功能范围

界面必须覆盖以下 P0 能力：

1. 首次启动：选择中文/英文，检查 Git、Claude Code、Codex 是否可用及是否需要登录。
2. 首页三个入口：
   - 新建产品（Beta）：仅使用内置 Vue 3 + Vite + TypeScript 标准 Web 模板；
   - 打开电脑中的项目；
   - 从 GitHub 导入：只 Clone 公开仓库、阅读 README/许可证、生成手动安装指南，不自动安装依赖，不自动运行陌生代码。
3. 用自然语言描述要求，必要时最多进行三组普通语言澄清。
4. 用用户能理解的语言确认“这次会做什么、不会做什么、怎样才算完成”。
5. 双 AI 闭环：开发 → 首次审核 → 一次修改 → 二次审核 → 用户确认。
6. 任务开始前可互换开发者和审核者；开始后锁定角色。
7. 真实工作时间线：阶段、当前动作、耗时、等待、失败、重试、中断恢复。
8. 证据与报告：改动文件、真实测试、Git 差异、审核结论和七类 Markdown 报告，但普通用户默认只看摘要。
9. 重启恢复：关闭应用后再次打开，能清楚提示并继续未完成任务，不重复已经完成的操作。
10. 简体中文与英文切换。

本版明确不设计为主要功能：

- 注册、登录 Nova 账号；
- SDKMAX 充值、模型商城、400 模型入口；
- 自动部署、服务器、域名、Docker、Nginx 或生产数据库管理；
- 自动安装或运行任意 GitHub 项目；
- 私有 GitHub 授权、自动 Push、自动创建 PR；
- 团队协作、项目看板、复杂仪表盘；
- 完整 IDE、代码编辑器或默认展示终端；
- AI 用量检测、自动额度接力；
- 原始思维链或无限自动返工。

任何新增想法只登记到 `docs/backlog.md`，不得混入 v0.1.0 设计。

## 六、总体体验目标：真正“傻瓜化”

“傻瓜化”不是幼稚化，也不是堆满说明文字。界面应专业、安静、可信、克制，视觉气质贴近 Claude Code：温和、自然、留白充分、低噪声、不过度科技化。

每个页面必须让用户在 5 秒内回答：

1. 我现在在哪里？
2. Nova 正在做什么或需要我做什么？
3. 我下一步只需要点哪个按钮？

具体要求：

- 一个页面只突出一个主要任务和一个主按钮。
- 优先使用生活化动词：如“选择项目”“告诉 Nova 你想改什么”“确认本次工作”“正在检查”“需要你确认”。
- 技术名词必须转换为普通语言。确需保留时，先给普通解释，再在括号或技术详情中显示术语。
- Git、CLI、diff、SHA、stdout/stderr、退出码、JSON、命令行等默认隐藏到“查看技术详情”。
- 错误信息采用三层结构：发生了什么 → 是否影响项目 → 用户现在怎么做；原始日志折叠显示。
- 不把用户扔进空白聊天框。输入区应提供清晰问题、示例和可选引导。
- 不让用户在同一页同时理解项目、AI、Git、任务、证据和日志。
- 危险或不可逆操作必须明确说明影响并二次确认；普通操作不要频繁打断。
- 不以动画或虚假百分比伪造进度；未知进度显示真实当前动作和已用时间。
- 不显示模型私有思维链，只显示可公开的工作摘要、工具动作和真实证据。
- 不用“AI 说完成了”代表完成。必须分别显示：系统证据、Codex 审核、用户确认。

## 七、信息架构与关键页面

请基于真实仓库进一步校正，但设计至少覆盖以下页面和状态。

### 1. 首次启动引导

- 欢迎与一句话价值说明；
- 中文/English 选择；
- 环境检查；
- “已准备好 / 需要登录 / 尚未安装 / 检查失败”的普通语言解释；
- 每个异常只给一个明确下一步；
- 环境未准备好时允许安全退出，不能进入死路。

不要把首次启动设计成开发环境配置面板。

### 2. 首页

首页只突出三个大入口：新建产品（Beta）、打开电脑中的项目、从 GitHub 导入。

需要明确推荐最适合零基础用户的入口，并用一句话解释每个入口适合什么情况。不得用复杂侧边栏、数据统计、最近活动流淹没入口。可在次要区域显示最近项目，但不能抢夺主视觉。

### 3. 新建产品（Beta）向导

- 产品名称；
- 保存位置；
- 用一句话描述产品；
- 创建前摘要；
- 目录非空时禁止覆盖并用普通语言解释。

不要让用户选择技术栈、框架、数据库或模板市场。

### 4. 打开电脑中的项目

- 选择目录；
- 用普通语言展示“项目可以开始 / 项目还有未保存的改动 / 这里不是项目 / 缺少必要工具”；
- 用户已有未提交修改必须明显保护，但避免用恐吓式警告；
- README、AGENTS、CLAUDE 等规则读取结果只显示摘要。

### 5. 从 GitHub 导入

- 粘贴公开 GitHub 地址；
- 选择保存位置；
- Clone 进度和网络失败状态；
- README/许可证摘要；
- 普通语言安装指南；
- 明确提示“Nova 不会自动运行刚下载的陌生程序”。

不要出现“自动安装并运行”主按钮。

### 6. 描述需求与确认范围

- 输入区问题应为“你希望这个产品有什么变化？”；
- 提供贴近日常表达的示例；
- 澄清问题使用可点选选项，并保留“自己填写”；
- 确认页用三块内容表达：本次会做、暂时不做、完成标准；
- 启动任务前再展示开发者与审核者角色，默认 Claude Code 开发、Codex 审核，允许一键互换；
- 用普通语言解释“一个负责做，一个独立负责检查”。

### 7. 工作任务页

建议采用：左侧轻量项目/任务导航，中部主工作区，右侧可收起的结果与证据详情。不要做成 IDE 三栏复刻。

中部首先展示：

- 当前阶段；
- 当前正在做的事情；
- 已运行时间；
- 当前是否需要用户操作；
- 唯一主操作按钮。

时间线阶段：需求确认 → 开发 → 首次审核 → 修改 → 二次审核 → 用户确认 → 完成。

每个节点显示角色、状态、开始/结束时间和一句话摘要。技术动作、命令和原始日志默认折叠。审核阶段必须醒目标明“Codex 正在独立检查，不能修改项目”。

### 8. 失败、中断与恢复

至少设计：

- CLI 未安装；
- 未登录；
- 网络中断；
- 命令失败；
- 用户取消；
- 应用被关闭后恢复；
- 首审不通过；
- 二审仍不通过；
- 工作区存在用户修改；
- GitHub 地址错误、无 README、无许可证、目标目录非空。

每种状态都要给普通解释、影响范围、推荐动作和备选动作。失败绝不能显示为绿色完成。

### 9. 完工确认页

清晰分开三项：

- Nova 已核对的真实结果；
- Codex 的独立审核结论；
- 等待用户体验并确认。

主按钮使用“我已检查，符合需要”之类的普通语言。还不满意时，不得进入无限自动修改；应创建新一轮任务并保留上一轮记录。

### 10. 技术详情与报告

技术详情是辅助层，不是主界面。用渐进披露呈现：普通摘要 → 变更与测试 → 原始命令/日志。

七类任务 Markdown 报告应能被用户找到和打开，但不要要求用户理解文件名。界面可以显示为“本次要求、开发结果、测试结果、首次检查、修改结果、再次检查、最终结果”。

## 八、视觉规范方向

- 风格关键词：干净、温和、克制、可信、轻量、桌面原生感。
- 参考 Claude Code 的低噪声审美，但不得机械复制品牌资产、商标、专有图标或具体页面。
- 采用温暖的中性色背景、清晰的内容层级和一个克制的强调色；避免大面积纯黑、荧光色、赛博朋克、发光边框和炫技渐变。
- 圆角、阴影、边框和动画均应轻量一致。
- 正文优先可读性，不用过小字号或低对比灰字。
- 状态不能只靠颜色区分，必须同时有文字和图标。
- 成功色只用于三方完成条件真实满足之后。
- 支持常用 Windows 窗口尺寸、窗口缩放以及系统 125%/150% 缩放。
- 中文与英文长度不同，布局不能依赖固定短文案。
- 支持键盘导航、可见焦点、合理 Tab 顺序及基础无障碍对比度。
- 动效仅用于状态过渡和反馈；尊重减少动态效果设置。

请明确给出颜色、字体、字号、间距、圆角、阴影、图标、按钮、输入框、卡片、状态标签、时间线、抽屉、弹窗和空状态的设计 Token 与组件规则。

## 九、必须制作的完整状态

不要只设计理想成功路径。至少覆盖：

- 首次使用与再次使用；
- 空状态、加载状态、处理中、等待用户；
- 成功、警告、错误、取消、重试；
- 无输出但仍在执行的长任务；
- 高频日志与超长内容；
- 中文、英文、长文案；
- 小窗口与最大化窗口；
- 键盘焦点；
- 应用重启后的任务恢复；
- 用户已有文件/改动保护；
- 审核 PASS、PASS WITH NOTES、FAIL；
- 技术详情收起与展开。

# Nova V1 MVP 产品开发文档

**版本：** V3.0  
**文档性质：** 产品需求、用户体验、技术实现与验收基线  
**产品形态：** 独立 Windows 桌面客户端  
**建议技术栈：** Tauri 2 + Vue 3 + TypeScript + Rust + SQLite  
**项目目录：** `D:\nova`  
**默认协作模式：** Codex 开发，Claude Code 审核  
**备选协作模式：** Claude Code 开发，Codex 审核  
**第一版账号策略：** 无需注册，所有任务数据默认保存在本机  
**界面语言：** 简体中文、英文

---

## 一、执行摘要

### 1.1 产品定义

Nova 是一个让普通人通过自然语言，协调 Codex 和 Claude Code 完成开发、审核、修改和完工确认的独立桌面客户端。

Nova 不重新实现 Codex 或 Claude Code 的编程能力，也不依赖它们的桌面界面。Nova 通过本机 CLI 适配器调用两个工具，负责用户交互、需求整理、角色分工、任务交接、进度展示、证据收集、Markdown 文档留存和最终完工判断。

### 1.2 V1 唯一核心价值

> **用户只需要说清楚想做什么，Nova 负责组织一个 AI 开发、另一个 AI 独立审核。**

### 1.3 V1 核心闭环

> 需求确认 → 开发 → 首次审核 → 修改 → 二次审核 → 完工确认

### 1.4 V1 三个入口

1. **新建产品（Beta）**：基于一个内置标准 Web 产品模板创建本地产品。
2. **打开电脑中的项目**：选择一个已有本地项目进入开发审核流程。
3. **从 GitHub 导入**：只负责克隆到本地、阅读 README、生成手动安装调试指南，并协助用户处理安装过程中遇到的问题。

### 1.5 V1 明确不做

- 不自动安装任意 GitHub 项目的依赖。
- 不自动运行任意 GitHub 项目。
- 不自动部署到线上。
- 不管理服务器、域名、Docker、Nginx 或生产数据库。
- 不做项目管理、团队协作和工作流编辑器。
- 不做 400 个模型选择器。
- 不做 Codex/Claude Code 额度自动接力。
- 不展示模型私有的原始思维链。

## 二、产品背景与真实用户问题

Nova 来源于 SDKMAX 项目的真实开发经验。典型流程是：用户提出业务要求，由 Codex 开发，Claude Code 审核，Codex 根据审核意见修改，Claude Code 再次审核，最后用户根据多份报告判断是否完成。

这套方式能够提高质量，但对非技术用户存在以下问题：

- 不知道如何把普通需求写成专业开发提示词。
- 不知道应该让哪个 AI 做什么。
- 在 Codex、Claude Code 和 ChatGPT 之间频繁复制内容。
- 审核意见不能自动交回开发 AI。
- 很难判断 AI 所说的“完成”是否有真实证据。
- 长时间运行时，不知道 AI 是否仍在工作。
- Markdown 文档散落，缺少统一命名和留存规则。
- 看不懂代码、Git Diff、测试日志和技术错误。

Nova V1 将这段人工流程产品化，但不扩大到自动部署、通用环境管理或开放式 Agent 自动化。

## 三、产品定位与品牌表达

### 3.1 一句话定位

> **Nova 是面向非技术产品建设者的双 AI 开发与验收助手。**

### 3.2 V1 产品承诺

> **不需要编写专业提示词，也能组织两个 AI 完成一次可信的产品开发或修改。**

### 3.3 推荐 Slogan

中文主口号：

> **一个 AI 开发，另一个 AI 验收。**

中文辅助口号：

> **说出你的想法，把开发流程交给 Nova。**

英文主口号：

> **One AI builds. Another verifies.**

英文辅助口号：

> **Describe what you need. Nova coordinates the work.**

### 3.4 目标用户

- 没有代码开发背景的产品所有者。
- 使用 AI 或外包获得现有产品，需要继续迭代的人。
- 能描述业务需求，但不会编写开发提示词的人。
- 使用 Codex 和 Claude Code，但不愿重复复制上下文的人。
- 希望第二个 AI 独立审核开发结果的人。

### 3.5 V1 不作为主要目标的用户

- 需要完整 IDE 的专业程序员。
- 需要自由编排多 Agent 的高级用户。
- 需要团队项目管理的研发组织。
- 需要通用本地部署和服务器运维的人。

## 四、产品边界与原则

### 4.1 独立客户端，复用 CLI 能力

Nova 是独立桌面客户端，拥有自己的品牌、界面、任务状态、文档和交接协议。Codex 与 Claude Code 是其背后的 AI 执行工具。

Nova 不控制 Codex 或 Claude Code 的桌面窗口，不依赖屏幕点击自动化。V1 通过适配器启动本机 CLI 子进程，解析其结构化输出或可识别的事件输出。

### 4.2 固定闭环优先

Nova V1 不允许用户设计任意工作流。系统只提供一条标准流程，并允许开发与审核角色互换。

### 4.3 简单界面，真实后台

前台可以把技术语言转换为普通语言，但不得隐藏关键风险，不得把未执行的测试显示为通过，不得把 AI 的文字声明当成真实文件、Git 或进程状态。

### 4.4 用户最终拥有决定权

审核 AI 可以给出技术结论，但“已完工”必须同时满足真实证据、审核结论和用户效果确认。

## 六、三个入口的详细设计

### 6.1 新建产品（Beta）

#### 目标

让用户从一个自然语言想法开始，基于 Nova 内置且经过验证的标准 Web 模板，建立一个本地产品并进入双 AI 开发审核闭环。

#### 第一版模板限制

V1 只内置一个模板，建议为：

> Vue 3 + Vite + TypeScript 标准 Web 产品模板

模板应当预先具备：

- 固定目录结构；
- 固定启动和构建命令；
- 基础路由；
- 基础响应式布局；
- 基础测试框架；
- ESLint 或等价静态检查；
- 中英文国际化结构；
- 示例环境变量文件；
- 不包含数据库、支付、登录和云端依赖。

#### 用户流程

1. 点击“新建产品（Beta）”。
2. 输入产品想法。
3. Nova 提出最多三组关键问题。
4. Nova 生成产品定位、目标用户、第一版功能和不做内容。
5. 用户确认产品方案。
6. Nova 生成项目级 Markdown 文档。
7. Nova 从内置模板创建本地项目并初始化 Git。
8. 进入标准开发审核闭环。

#### 复杂度控制

当用户要求支付、复杂权限、即时通信、生产数据库或多服务架构时，Nova 应提示：

> 这个产品超过了当前 Beta 的自动建设范围。Nova可以先帮你完成一个不包含复杂后台的演示版本。

### 6.2 打开电脑中的项目

#### 目标

让用户选择一个已经存在的本地项目，并直接进入需求、开发和审核流程。

#### Nova 检查内容

- 目录是否存在且可读；
- 是否为 Git 仓库；
- 当前分支和工作区状态；
- 是否存在未提交修改；
- 是否存在 README、AGENTS、CLAUDE 或项目规则文件；
- Codex和Claude Code是否可以访问该目录。

#### V1边界

Nova不承诺自动修复项目环境。项目无法运行时，Nova可以让开发AI诊断并给出建议，但不得把“环境诊断”误报为“项目已可运行”。

### 6.3 从 GitHub 导入

#### 目标

降低用户下载和理解开源项目的门槛，不承担通用自动运行和部署。

#### V1执行范围

1. 用户粘贴公开 GitHub 仓库地址。
2. 验证地址并读取公开元数据。
3. 用户选择本地保存目录。
4. Clone到独立目录。
5. 阅读 README、许可证和主要安装文档。
6. 识别可能的技术栈、环境、依赖和启动步骤。
7. 生成普通语言的手动安装调试指南。
8. 提供命令复制按钮，但不自动执行安装命令。
9. 用户粘贴错误、上传截图或选择日志后，开发AI协助诊断。
10. 用户确认项目已准备好后，进入标准开发审核闭环。

#### V1不做

- 不自动执行 `npm install`、`pip install`、Docker等命令；
- 不自动创建数据库；
- 不自动申请管理员权限；
- 不自动运行第三方安装脚本；
- 不自动推送回 GitHub；
- 不处理私有仓库。

#### 用户界面文案

入口名称：

> 从 GitHub 导入

辅助说明：

> 下载开源项目，阅读安装说明，并在遇到问题时获得帮助。

## 七、需求—开发—审核闭环

### 7.1 状态机

任务状态必须由 Nova 明确控制：

1. `DRAFT`：用户正在描述需求。
2. `REQUIREMENT_CONFIRMATION`：等待用户确认需求卡。
3. `DEVELOPING`：开发AI执行任务。
4. `COLLECTING_EVIDENCE`：Nova收集真实证据。
5. `FIRST_REVIEW`：审核AI首次审核。
6. `FIXING`：开发AI根据审核意见修改。
7. `SECOND_REVIEW`：审核AI二次审核。
8. `USER_ACCEPTANCE`：等待用户确认效果。
9. `COMPLETED`：证据、审核与用户确认全部满足。
10. `NOT_COMPLETED`：存在阻断问题。
11. `PAUSED`：用户暂停或进程中断。

任何异常退出不得直接跳转为 `COMPLETED`。

### 7.2 需求输入

输入框提示：

> 例如：给用户列表增加按邮箱搜索功能，不能影响原来的分页和权限。

Nova可以辅助询问：

- 你想修改什么？
- 现在是什么情况？
- 希望变成什么样？
- 哪些功能不能受到影响？
- 怎样才算完成？

### 7.3 需求确认卡

确认卡必须包含：

- 原始需求；
- Nova整理后的目标；
- 本次包含内容；
- 本次不包含内容；
- 禁止影响的原有功能；
- 验收标准；
- 尚未确认的问题。

按钮只有：

- 理解正确，开始开发；
- 修改需求。

### 7.4 开发任务

Nova根据当前角色配置生成开发任务包，内容包括：

- 项目目录和允许访问范围；
- 项目规则与相关文档索引；
- 用户原始需求；
- 已确认需求和验收标准；
- 禁止扩大范围；
- 必须执行的检查；
- 文档输出要求；
- 结构化结束状态。

### 7.5 证据收集

开发AI结束后，Nova独立采集：

- 子进程退出码；
- Git状态；
- 实际修改文件；
- Git Diff；
- AI报告中声称执行的命令；
- 可验证的测试输出；
- 未执行的检查；
- 未解决问题。

### 7.6 首次审核

审核AI默认只读。必须核对：

- 需求完成度；
- 范围是否失控；
- 原有功能风险；
- 实际代码改动；
- 测试证据；
- 安全和隐私问题；
- 开发文档是否与代码一致。

审核结论只能是：

- `APPROVE`：可以进入用户确认；
- `CHANGES_REQUIRED`：需要明确修改；
- `INSUFFICIENT_EVIDENCE`：证据不足，不能确认。

### 7.7 修改

审核未通过时，Nova自动生成修复任务包，包含：

- 原始需求和验收标准；
- 当前改动；
- 首次审核问题清单；
- 每个问题的严重等级；
- 必须重新执行的测试；
- 禁止扩大修改范围；
- 需要更新的Markdown文档。

### 7.8 二次审核

二次审核重点检查：

- 首次问题是否全部关闭；
- 是否引入新问题；
- 相关测试是否重新执行；
- 文档是否更新；
- 原始需求是否仍然满足。

V1自动执行一次修改和一次二次审核。二次审核仍未通过时，状态为“尚未完工”，由用户决定是否开始下一轮。

### 7.9 完工判定

只有同时满足以下条件，才能显示“已完工”：

- 开发进程正常结束；
- 实际存在与需求相关的改动，或任务合法地判定无需改动；
- 必要测试已经真实执行；
- 没有阻断性测试失败；
- 审核AI最终通过；
- 高风险问题全部关闭；
- 用户确认实际效果。

最终状态包括：

- 已完工；
- 等待用户确认；
- 尚未完工；
- 无法确认；
- 已暂停。

## 八、AI角色与互换

### 8.1 默认模式

> Codex 开发 → Claude Code 首次审核 → Codex 修改 → Claude Code 二次审核

### 8.2 反向模式

> Claude Code 开发 → Codex 首次审核 → Claude Code 修改 → Codex 二次审核

### 8.3 用户选择方式

任务页顶部显示一个简单的“协作模式”控件：

- Codex开发，Claude Code验收（推荐）；
- Claude Code开发，Codex验收。

新用户默认推荐模式。Nova记住上一次选择，但每个新任务都显示当前角色，避免误解。

### 8.4 权限规则

- 开发AI：允许在当前项目目录读写并执行经授权的开发、构建和测试命令。
- 审核AI：默认只读，不允许修改项目文件。
- 返工阶段：只有原开发AI获得写权限。
- 用户凭据、密钥和系统敏感目录不得自动加入AI上下文。

## 九、AI工作时间线与“思考过程”

### 9.1 产品目标

长时间任务中，用户必须持续知道：

- Nova是否仍在运行；
- 当前由哪个AI工作；
- 当前在做什么；
- 最近完成了什么；
- 是否正在等待用户；
- 是否出现停滞或错误。

### 9.2 展示边界

Nova展示的是可理解、可验证的工作过程，不展示模型私有的原始思维链。

允许展示：

- 工作计划；
- 当前目标；
- 阶段性摘要；
- 正在读取或修改的文件；
- 执行命令；
- 测试进度；
- 关键决策摘要；
- 遇到的问题；
- 最近活动时间。

不展示：

- 未经整理的内部推理；
- 大段自言自语；
- 无法验证的“正在深入思考”；
- 密钥、Token和敏感环境变量。

### 9.3 时间线样式

参考 Codex 和 Claude Code 的简洁事件时间线：

```text
● Codex 正在工作 · 06:32

✓ 已读取项目规则
✓ 已找到用户列表相关页面
✓ 已制定修改方案
● 正在增加邮箱搜索功能
○ 等待执行测试
○ 等待 Claude Code 独立验收

最新进展：12 秒前
为了避免影响原有分页，本次搜索条件将与分页参数共同保存。
```

### 9.4 事件类型

每条时间线事件至少包含：

- 事件ID；
- 任务ID；
- 时间；
- 执行角色；
- 阶段；
- 事件类型；
- 面向用户的摘要；
- 可选技术详情；
- 来源是CLI、Nova采集还是AI摘要。

事件类型建议：

- `PLAN_CREATED`
- `FILE_READ`
- `FILE_CHANGED`
- `COMMAND_STARTED`
- `COMMAND_FINISHED`
- `TEST_STARTED`
- `TEST_FINISHED`
- `DOCUMENT_WRITTEN`
- `REVIEW_FINDING`
- `WAITING_FOR_USER`
- `WARNING`
- `ERROR`
- `COMPLETED`

### 9.5 防止假进度

- 有真实CLI输出或系统事件时更新进度。
- 30秒没有新事件：显示“任务仍在运行，正在等待AI返回”。
- 90秒没有新事件：显示“工作时间较长，Nova正在检查运行状态”。
- 子进程仍存活时不能伪装失败，也不能用虚假内容刷新时间线。
- 子进程异常退出时显示“工作意外停止”，并提供重试、查看详情和保存任务。
- 等待权限确认时必须明确显示“需要你确认”。

## 十、Markdown文档体系

### 10.1 设计目标

Markdown文档用于：

- 保存用户需求；
- 保留开发决策；
- 给审核AI提供可靠上下文；
- 保存测试与审核证据；
- 支持任务中断恢复；
- 为未来跨AI接力提供基础。

### 10.2 两层文档结构

#### 项目级长期文档

新建产品时默认生成：

```text
docs/
├── PRODUCT_PLAN.md
├── ARCHITECTURE.md
├── DEVELOPMENT_RULES.md
├── TESTING_GUIDE.md
└── README.md
```

已有项目不强制创建或覆盖这些文件。只有用户确认后，Nova才能在现有`docs`目录中新增文档。

#### Nova任务级文档

所有入口统一保存：

```text
.nova/
└── tasks/
    └── <task-id>/
        ├── REQUIREMENT.md
        ├── DEVELOPMENT_REPORT.md
        ├── TEST_REPORT.md
        ├── FIRST_REVIEW.md
        ├── FIX_REPORT.md
        ├── SECOND_REVIEW.md
        └── FINAL_RESULT.md
```

`.nova`默认作为本地任务目录，是否提交Git由用户决定。

### 10.3 文档责任

| 文档 | 主要生成者 | 内容依据 |
| --- | --- | --- |
| REQUIREMENT.md | Nova | 用户输入和确认卡 |
| DEVELOPMENT_REPORT.md | 开发AI | 计划、实现和已知问题 |
| TEST_REPORT.md | Nova为主 | 真实命令、退出码和输出 |
| FIRST_REVIEW.md | 审核AI | 文档、Diff和证据 |
| FIX_REPORT.md | 开发AI | 修复清单和复测 |
| SECOND_REVIEW.md | 审核AI | 问题关闭和最终审核 |
| FINAL_RESULT.md | Nova | 所有真实证据和用户确认 |

### 10.4 Token控制

审核阅读文档会消耗Token，但这是必要质量成本。Nova必须控制上下文：

- 建立文档索引；
- 只读取与本次任务相关的章节；
- 不重复发送同一内容；
- Git、退出码和测试输出由Nova直接采集；
- 大型Diff先建立文件索引，再按风险读取；
- 不把全部历史任务文档发送给审核AI；
- 项目长期文档只在相关时读取。

### 10.5 审核AI必须阅读

- REQUIREMENT.md；
- 与任务相关的项目规则；
- DEVELOPMENT_REPORT.md；
- TEST_REPORT.md；
- 实际Git Diff和修改文件；
- 首次审核后的修复阶段还需读取FIRST_REVIEW.md和FIX_REPORT.md。

## 十一、界面与视觉设计

### 11.1 设计风格

整体参考 Codex 和 Claude Code 的克制、专业、低噪声体验：

- 大量留白；
- 清晰层级；
- 低饱和配色；
- 轻量圆角；
- 细边框；
- 浅色与深色主题；
- 动画用于状态反馈，不用于装饰；
- 默认隐藏代码和终端；
- 不复制任何一方的商标、图标和专有视觉资产。

### 11.2 推荐颜色角色

- Nova主色：深蓝灰或中性靛蓝；
- Codex开发状态：蓝绿色；
- Claude Code审核状态：暖橙色；
- 通过：柔和绿色；
- 需要修改：琥珀色；
- 阻断：克制红色；
- 普通背景：暖白/浅灰；
- 深色背景：深灰而非纯黑。

### 11.3 首页

标题：

> 今天想建设什么？

三个入口卡片：

1. **新建产品（Beta）**  
   从一个想法开始，使用标准Web模板建立产品。
2. **打开电脑中的项目**  
   继续开发或修改一个已有项目。
3. **从GitHub导入**  
   下载开源项目，阅读安装说明并获得调试帮助。

底部显示环境状态：

- 开发助手已准备；
- 验收助手已准备；
- 当前语言。

### 11.4 需求页

主要区域是自然语言输入框，顶部显示当前项目，底部显示当前协作模式。

主按钮：

> 整理我的需求

整理后切换为需求确认卡，主按钮变为：

> 理解正确，开始开发

### 11.5 任务工作台

推荐三栏结构：

- 左侧窄栏：当前产品、当前任务、最近任务；
- 中央主区：AI时间线、用户输入和必要确认；
- 右侧可折叠栏：本次修改、测试、文档和审核结论。

顶部固定显示：

> 需求确认 → 开发 → 首次审核 → 修改 → 二次审核 → 完成

右侧技术栏默认收起，普通用户通过“查看工作详情”展开。

### 11.6 完工页

顶部只显示一种明确结论：

- 已通过技术验收，等待你确认；
- 本次任务尚未完工；
- 无法确认，需要补充检查；
- 已完工。

内容包括：

- 完成了什么；
- 首次审核发现什么；
- 开发AI修复了什么；
- 二次审核是否通过；
- 哪些测试真实执行；
- 哪些内容没有检查；
- 是否可以恢复。

按钮：

- 确认已经完工；
- 继续修改；
- 查看专业报告。

V1如果未实现可靠恢复机制，不得显示“恢复修改前状态”按钮。

## 十四、技术架构建议

### 14.1 架构分层

1. **Vue界面层**：页面、时间线、双语、用户确认。
2. **工作流引擎**：状态机、角色分配、返工和完工门禁。
3. **AI适配层**：Codex CLI适配器、Claude Code CLI适配器。
4. **项目服务层**：目录、Git、规则和项目入口。
5. **证据服务层**：Diff、命令、进程和测试证据。
6. **文档服务层**：Markdown生成、索引、读取和版本。
7. **本地存储层**：SQLite任务索引和文件系统文档。
8. **安全层**：目录权限、敏感文件过滤和审核只读控制。

### 14.2 AI适配器统一接口

每个适配器至少实现：

- 检测CLI是否安装；
- 检测是否可调用；
- 启动任务；
- 接收标准输出和错误输出；
- 转换为时间线事件；
- 停止任务；
- 获取结束状态；
- 区分登录、额度、权限、进程和未知错误；
- 支持开发权限和审核只读权限。

### 14.3 本地数据

SQLite保存：

- 项目引用；
- 任务ID；
- 当前状态；
- 角色配置；
- 时间线事件索引；
- 文档路径；
- 审核结论；
- 用户确认。

大文本、Diff和Markdown保存在任务目录，避免全部塞入数据库。

### 14.4 安全要求

- 只访问用户明确选择的项目目录；
- 默认不读取`.env`、私钥、凭据目录；
- 日志自动遮盖常见密钥格式；
- 审核模式必须技术上限制写入；
- 不自动请求管理员权限；
- 不自动访问生产服务器；
- GitHub V1只支持公开仓库；
- Clone后不自动运行第三方脚本；
- CLI异常退出不得丢失任务记录。

## 十五、错误与异常体验

每个错误必须包含：发生了什么、当前数据是否安全、用户下一步可以做什么。

示例：

### Codex未安装

> 开发助手尚未准备好。安装Codex后即可开始开发。

> 验收助手需要先完成官方登录。Nova不会读取你的密码。

按钮：打开登录说明、重新检查。

### 开发进程中断

> 开发工作意外停止，已完成的记录和文档仍然保留。

按钮：重试、查看详情、暂时保存。

### 测试未执行

> 当前没有足够的测试证据，不能确认任务已经完工。

按钮：让开发助手补充检查、查看原因。

### GitHub项目无法安装

> Nova已经下载项目，但当前电脑缺少运行条件。请按照以下步骤手动准备；遇到错误时可以把信息交给Nova分析。

邀请至少10名非技术用户完成一个小任务：

- 8人能识别三个入口的区别；
- 8人能独立描述并确认需求；
- 7人能完成完整双AI闭环；

- 用户不需要手工编写专业提示词；

## 二十、最终产品描述

> **Nova是一个面向普通人的独立AI开发客户端。用户可以从一个标准模板新建产品、打开电脑中的已有项目，或把GitHub开源项目下载到本地。用户只需用自然语言描述需求，Nova便会组织Codex和Claude Code分别承担开发与独立审核，自动传递文档和证据，完成修改与二次审核，并通过持续可见的工作时间线让用户了解当前进展。**

Nova V1只做好一个核心结果：

> **让普通用户不需要编写专业提示词，也能完成一次有记录、有审核、有证据的产品开发或修改。**
